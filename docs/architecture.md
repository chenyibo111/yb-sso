# 飞书企业成员单点登录设计

## 目标

由已有飞书测试企业负责成员身份认证；独立的 Go 登录中心为多个本地项目提供统一的 OIDC 登录入口。第一阶段只服务一个飞书企业及其可用范围内的成员。

## 方案

业务项目不直接连接飞书。项目发现未登录时跳转到 Ory Hydra（Go 编写的 OIDC 服务）；Hydra 把登录挑战交给本项目的 Go 服务。Go 服务将用户送往飞书授权页，收到回调后在服务端换取身份信息并确认企业成员资格，再向 Hydra 提交稳定的内部用户 ID（OIDC `sub`）。Hydra 完成面向业务项目的授权码流程。

这种双层结构让新增业务项目只需接入 OIDC，不需重复处理飞书协议或飞书应用凭证。Hydra 管理客户端、签名密钥和协议令牌；本项目的 Go 服务负责飞书认证与成员规则。PostgreSQL 保存 Hydra 的持久状态。

## 数据边界

- 内部用户 ID 由 SSO 生成且保持稳定；飞书 `open_id` 只作为该飞书应用中的外部身份键，不直接用作业务项目的用户主键。
- 飞书企业自建应用及其可用范围限定谁可以登录。登录中心在每次新登录时向飞书换取用户信息，拒绝没有 `open_id` 或 `tenant_key` 不匹配的响应。当前没有额外的通讯录状态查询或成员失效事件处理；现有会话仍按各自有效期结束。
- 各业务项目各自管理业务权限；SSO 第一阶段只表达身份及基础成员状态。
- App Secret 不写入仓库。当前 Compose 中的 Hydra 系统密钥和数据库密码仅用于本地开发，线上使用前必须替换；回调地址必须精确登记，演示客户端使用授权码和 PKCE。
- 退出流程使用 Hydra 的 OIDC 后端退出通知。由于 Hydra 2.3 异步发送通知，演示项目访问受保护页面前还会通过 SSO 查询 PostgreSQL 中的撤销状态；该接口不可用时拒绝访问。

## 非目标

第一阶段不实现本地密码、公开注册、多企业租户、自动同步飞书通讯录、互联网部署或自制密码学协议。

## 实施前置条件

- 在飞书测试企业创建企业自建应用，配置两名成员可使用及登录回调地址。
- 可在开发机器安装 Go，也可以使用 Go Docker 镜像编译本机可执行文件。
- 确定本地回调地址能通过飞书开发者后台校验。若不能，使用临时 HTTPS 隧道，仅供开发联调。
